# iPlay v0.20.17 listening audit and implementation brief

Audited tag `v0.20.17`, commit `80cb82d33b58d89126d7c9d6ba50e8995b7b177d`. This is a source audit with targeted tests and deterministic TypeScript probes. Device playback, live provider inventory and listener preference were outside the measured baseline. Paths below start at `discovery-demo/`. [Pinned source](https://github.com/jyoung2000/iPlay/tree/80cb82d33b58d89126d7c9d6ba50e8995b7b177d/discovery-demo)

## What decides the next song today

| Decision | Release behavior |
|---|---|
| Find candidates | The installed apps use the TypeScript LocalApi. Discovery gathers related tracks, radio and artist results plus exploration candidates, deduplicates recordings, enriches a bounded subset, and appends a batch to the existing queue. The low-water check runs at five remaining on an eligible skip or completion. A separate optional, rate-limited mood top-up can request more candidates after a completion. |
| Rank and select | Seed audio, tags, artist, service relationships and tempo contribute where known. Global feedback, freshness, novelty and listening taste affect affinity. The built-in score discounts thin evidence. The active preset can change weights or substitute a bounded formula. Selection then accounts for exposure, tier targets, recent similarity, artist caps and seed representation. A high raw score alone does not guarantee the next slot. |
| Adapt to mood | This feature estimates recent musical taste from actions, genre families, finer tags and available 512-dimensional sound vectors. It retains up to 32 signals over 90 minutes with a 15-minute half-life. Current song +3, star +5, Find similar +6, dislike −6. The normal planner chooses up to 12 upcoming movable songs and can prioritize three matching lead tracks. |
| Shuffle and play | Discover materializes an order, usually avoiding consecutive primary artists where possible. The transport also checks availability, heard history and the four-song artist-run rule. Saved-list shuffle picks from its own round. Android has native round, cue, repeat and screen-off behavior, and requests mood ordering from the catalogue engine when the phone UI is closed. |

## Findings and regression fixtures

**1. A feedback re-rank can add candidates and move a hand-added song. High priority, reproduced at the merge boundary.** `local-api.ts:2370,2391` stores previous rows plus the gathered pool, then selects up to pool length during re-rank. `web/src/util.ts:508` prepends protected rows and accepts the remaining returned keys. In a direct call, current queue [A, B, PIN, C] with A played and ranked response [C, NEW, B] became [A, PIN, C, NEW, B]. The pin moved from slot three to two and NEW entered. A previously queued movable song omitted by selection can disappear. Discovery and feedback use different merge paths, so UI membership can also diverge from stored last_result. Limit re-rank to current queue membership, retain unscorable eligible rows, and scatter ranked movable rows into movable slots. Define explicit removals, adds and top-ups as separate membership changes.

**2. Discover shuffle often misses the session mood. High priority, reproduced in the order function and traced through React.** `web/src/App.tsx:727–755,831–850` debounces the mood request 600 ms. Discover retains its shuffled order when the answer arrives. The shuffle effect does not depend on fit or adventurousness, and the known-order branch of `engine/shuffle-order.ts` preserves known keys even if called again. With [B,C,D] already planned, returning full confidence and best fit for D kept [B,C,D]. An existing fit can influence a fresh draw, but the first async answer or a later change of taste can miss the rest of the round. Preserve the cued next track, then redraw only the uncommitted tail on a meaningful new mood revision. A routine render, polling tick or identical fit must leave it alone.

**3. Custom discovery can disable mood scoring for an entire queue. High priority, reproduced.** `engine/local-api.ts:1775,1839` marks custom and similar results as added. `engine/mood-apply.ts:moodMovable` excludes added items. `App.tsx:730` exits when fewer than two rows are movable, before requesting even score-only fits. A fixture of four custom rows gave zero movable rows. This also affects a shuffled saved list when the playing index leaves fewer than two rows ahead even though shuffle can choose unheard rows elsewhere. Distinguish manual pins and generated origins with backward-compatible decoding. Fit all eligible shuffle candidates independently of whether a sequential reorder is possible. Decide explicitly which similar results are intentionally pinned.

**4. Obsolete mood answers can affect a new context. High priority, traced.** `App.tsx:727–756` cancels a timer, but a started promise remains live. The request sequence increments after both early returns. Turning mood off, leaving the queue for search, or shrinking to one candidate can leave the previous token valid. Queue/hidden membership is absent from the effect dependencies. `android/.../PlaybackService.kt:moodNudge` applies a returned order without matching the captured current item or queue revision, although `EnginePlayer.applyMood` does check page/radio ownership. At both boundaries check context, current playback instance, queue revision, effective settings and candidate membership before applying an answer. Coalesce re-plans, preserve distinct feedback events and clear obsolete fit and label state.

**5. Discover repeat-all confuses discovery history with round exhaustion. High priority, reproduced in composition.** `App.tsx:235–245,616–622` unions lifetime starts/completions/skips with the current round. On wrap only the round clears. With four ready songs all on record, the tagged arrangeShuffle + stepQueue functions produced A,B,C,D,A,B,C,D in a simple fixture but flagged every transition as a wrap. Rebuilding the round cannot draw any coming songs because they are all permanently heard. Up Next also excludes wrapped picks at `App.tsx:817`. Separate long-term discovery eligibility from the repeat round. With repeat off, preserve the existing once-heard rule. With repeat all and an exhausted pool, commit one fallback round and track its progress. Prefer newly available unheard discoveries per existing behavior, honor the ready-file gate and prevent a boundary repeat when alternatives exist. Test actual UI Next, native cue and auto-advance.

**6. Listening origin, impressions and playback success can mislead the algorithm. High priority for quality measurement.** `App.tsx:1158–1201` sends origin=queue for the shared listen callback. `engine/local-api.ts:listeningGuard` explicitly relies on origin and membership to authorize a network top-up. A search play of a track also in Discover can therefore pass the queue-origin check. `App.tsx:582–589` records all filtered items as shown even when the Discover view is not visible, and marks them locally before persistence succeeds. `play()` records an item as started before setPlaying can lead to successful playback. Capture origin/list/queue ID at playback-instance creation, commit heard history after a confirmed start or explicit skip, and distinguish selected, visible, started, failed and qualified-listen events. Keep locally chosen history after actual audible starts, including partial plays. Verify double callbacks from the service and UI count once.

**7. Mood confidence and negative feedback need separate checks. Reproduced.** `engine/mood-queue.ts:buildMood,moodFit` calculates confidence from positive weight even without usable features. A star on an untagged track without audio produced confidence 0.8333 and an empty fit map. A dislike-only genre match produced fit 0.2 and confidence 0, so weighted shuffle ignores it. Sequential mood can still penalize negative matches. With one negative tag, affinity normalizes it against itself, so negative genre strength can stay maximal while the event ages. Calibrate usable positive and negative evidence separately, downweight uncertain/inferred tags, and test weak skips, missing duration and conflicting recent signals. Retain explicit track removals. At full confidence, Familiar currently gives a fit-1 song roughly 22,026 times the draw weight of a fit-0 song before artist constraints. Tune against multi-seed distributions and observed preferences.

**8. Artist concentration begins before shuffle. Reproduced for missing credits, traced for retrieval.** `engine/engine.ts:159,794–845` uses an empty primary-artist key as a shared cap. Five separately keyed candidates with missing artist credits yielded only two selections at the default cap. Avoid treating all unknown artists as one performer, and avoid rewarding missing metadata as novelty. `engine/artist-variety.ts:artistLoad` counts waiting rows excluding heard keys. It does not implement the recent-listens count suggested by the caller comment. `local-api.ts:moodWantsMore` can take three distinct tracks from one artist even when others have useful evidence. Measure source and artist concentration at retrieval, after ranking, and among ready tracks. Try bounded seed diversity or a soft recent-artist penalty only when alternate relevant artists exist. Keep direct artist searches and explicit plays intact.

**9. Re-ranking can reuse stale discovery settings. Traced.** `engine/local-api.ts:2391–2419` reconstructs the active algorithm config, feedback and taste, but inherits pool.ctx.settings, including adventurous and fresh, from the discovery run. Mood reads current settings independently. Test changing each setting/preset between discovery and feedback, both in memory and after restorePool. Build the effective context once per re-rank from current settings while retaining the pool's seed and candidate evidence. Compare identical fixed-pool runs with the same effective settings.

**10. Shuffle cost increases quickly on large accumulated queues. Measured indication.** Each draw in `engine/shuffle-order.ts:arrangeShuffle` repeatedly normalizes artists, scans and sorts counts, and splices the remaining array. One Node run with distinct artists took about 20 ms for 100 rows and 230 ms for 500. These are single host samples. Benchmark median/p95 before optimizing. Cache normalized artists and counts across draws, benchmark on the phone and keep deterministic seed injection for tests. Include readiness promotion, unknown credits, newly appended rows and hard manual-next priority in that benchmark.

## Acceptance matrix

| Scenario | Required result |
|---|---|
| Feedback, manual pin, concurrent top-up, restart | Only an explicit add/remove or a discovery batch changes membership. Every eligible pre-existing recording appears once. Manual pins keep their intended positions and the restored queue agrees. |
| Four ready tracks, all heard historically | Repeat off exhausts Discover. Repeat all completes a round without replacement and marks exactly one boundary per round. Saved-list rounds remain independent. |
| Up Next, crossfade, Android handoff | The announced eligible song is the one heard, including the wrap case. Eviction or removal recomputes the commitment once. Radio retains station shuffle. |
| Delayed mood, busy queue | Hold a mood request open, turn mood off or switch lists, then resolve it. The stale answer cannot change queue order, fit or title. New accepted mood affects only the uncommitted suffix. |
| Generated-only queue, saved list at final index, one movable row | Eligible rows still receive fit values. Album order remains fixed with shuffle off. Real manual pins and the current row stay fixed. |
| Star, skip, dislike, missing vectors | No-features star produces no actionable confidence. Negative-only evidence reduces early exposure of matching songs. A late skip is neutral. Same artist with different-sounding songs gets separate track evidence. |
| Search overlaps Discover, offscreen results, failed playback | A search listen does not authorize queue top-up. A hidden view contributes zero impressions. A failed-to-start item remains eligible for retry. |
| Quality and cost | On identical candidate pools and random seeds, record artist share/top-10 unique artists, consecutive runs, early repeats, fit of first three, skipped/liked rate on exposed items, p95 planning time, provider requests and bytes per playable addition. Report unavailable metrics explicitly. |

For the electronic-rap complaint, use a fixture with several liked artists in the same subgenre, an overrepresented artist, a jazz distractor, alternate provider IDs, and several songs with missing tags or audio. Run once with all songs ready and once with only the dominant artist cached. A retrieval failure, a scoring preference and a readiness bottleneck need different repairs. Proposed hard gates are zero unintended repeats, zero stale applies and zero unauthorized membership changes. Choose diversity and latency thresholds after establishing a device baseline. Use an opt-in chronological holdout of actually exposed songs for any personal-relevance claim. The repository's frozen synthetic benchmark measures invariants.

## Verification on the release tag

Node 24.22.3 with pnpm 10.33.0 and the web npm lockfile. The release checkout's default isolated pnpm layout left Vite and its React plugin unresolved from the web directory. For this audit, existing installed Aqua UI dependencies were temporarily linked into the root node_modules. No tracked source edits were needed. Run from discovery-demo/web after installing the dependencies.

```sh
npm test -- --maxWorkers=2 shuffle mood engine-v2 artist-variety ranking-formula
npm test -- --maxWorkers=2 engine/algorithms engine/engine.golden engine/queue-data-flow engine/discovery.integration engine/cold-start.integration engine/dislike-learning engine/playlist-queue engine/similar-sound.integration engine/allowance-lanes engine/benchmark.ab
```

First selection passed 180 tests across 18 files. Second selection passed 88 tests across 12 files. The first run also logged refused localhost connections from the test environment. Separate direct probes using the tagged TypeScript functions produced the examples in findings 1, 2, 3, 5, 7, 8 and 10. The React race, event-origin and settings findings are source traces. The audit did not run the full release suite or establish live recommendation quality.
